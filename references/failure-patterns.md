## Appendix. Common failure patterns

Common failure patterns in vendor datasets, listed here so QC reviewers know what to look for:

**No traces, only results.** Vendor reports pass rates but provides no model traces. Without traces you cannot verify how the model arrived at its score, whether the agent actually used the intended tools, or whether the grader is testing the right thing. This is the most common failure and the most basic.

**Single-model testing.** Vendor tested on one model (usually the strongest frontier model available) and reports results only for that. Without cross-model comparison, you can't tell whether difficulty is calibrated or whether the environment is broken. A task that's 65% on Opus might be 95% on Gemini or 5% on an open-source model.

**Averages without distributions.** Vendor reports '46% average over 5 rollouts' but doesn't show individual rollout results. The average is meaningless without the spread. Five rollouts at [44, 45, 46, 47, 48] tells a different story than [0, 0, 100, 100, 30].

**Rubric criteria too coarse.** Vendor's rubric has 2-3 criteria per task, all binary pass/fail. This is too thin for training signal. Partial credit requires fine-grained criteria. Aim for 8+ criteria per task for tasks with multi-step solutions, with each criterion targeting a specific step or sub-objective.

**Tasks too easy for the target model.** Vendor shows high pass rates as evidence of quality. High pass rates mean the opposite: the dataset provides minimal training signal because the model already handles these tasks. Look for the productive difficulty range, not the highest score.

**Contrived tasks masquerading as real workflows.** Tasks are created by experts in isolated settings, not derived from real work. The tell: tasks have perfect information, clear boundaries, and no ambiguity. Real work has messy inputs, missing context, and judgment calls. Tasks that feel like exam problems are probably exam problems.

**Grader rewards format over substance.** The grader checks whether the output matches a template (correct headers, correct number of decimal places, correct file format) without checking whether the actual content is correct. Post-trained models learn to produce correctly-formatted wrong answers.

**Training signal confined to narrow subtask.** The dataset nominally covers 'financial analysis' but all the trainable signal comes from a single subtask (e.g., DCF modeling) and the rest of the tasks are either too easy or too hard. The model improves on DCF and nothing else. Check the per-task hillclimbness distribution, not just the aggregate.

**Outcome-only rubrics when observable process is part of the construct.** A final answer may be sufficient when the objective is uniquely verifiable and multiple methods are valid; do not grade private reasoning or conformity to an intended path. Add process criteria only when observable behavior is itself the target capability or an explicit production constraint, such as tool permissions, required state transitions, intermediate artifact validity, forbidden side effects, an efficiency budget, or recovery from failure. Score the agent-visible transcript, actions, tool results, state changes, and artifacts, and retain those traces for audit without turning a valid alternative method into a failure.

**Static dataset sold as renewable.** The vendor claims the dataset will remain useful over multiple model generations, but the task set is fixed with no variant generation mechanism. When the next model upgrade ships, half the tasks will saturate overnight. Ask whether the dataset includes parameterized templates or procedural generation. If not, treat it as a depreciating asset with limited shelf life.

**Deterministic grader hides rubric failures.** The dataset uses a deterministic code grader that checks the binary outcome (did the exploit work, did the patch compile) but doesn't evaluate how the agent got there. The deterministic grader passes, so the dataset looks clean. But when you add a rubric-based process evaluation, you find the agent is brute-forcing, taking unrealistic shortcuts, or exploiting environment artifacts. Always test both layers if the task is complex enough to warrant process evaluation.

**Frontier collapse to a point.** When you run frontier shape analysis, the performance-vs-latency curve rises vertically and immediately plateaus. The model finds a high-scoring strategy at minimal compute and additional reasoning depth adds nothing. This is the Pareto frontier signature of a reward-hackable task set. The model has found a shortcut that the grader rewards without requiring the deep reasoning the task was designed to train. The reward hacking probes (stage 2) may not catch this if the shortcut produces outputs that look reasonable on surface inspection. The frontier catches it because it reveals the compute-performance relationship, and genuine capability always scales with compute within the productive range.

**Phase divergence without obvious reward misalignment.** The two-phase post-training frontier significantly outperforms the joint-training frontier, but the grader appears well-designed on manual inspection. This usually indicates a subtle proxy metric problem: the grader measures something that correlates with task performance at low capability levels but diverges at high levels. For example, a grader that rewards 'number of correct intermediate steps' might align with capability when the model is weak (more steps = better reasoning) but misalign when the model is strong (the model finds shortcuts that skip steps). The phase divergence catches this because phase 1 develops the shortcutting capability and phase 2 can't compress it into the grader's expected format.

**Banal mechanical failure mistaken for capability failure.** The agent fails because it cannot find a control, navigate a menu, or open the sub-window a practitioner would use. The observable trace shows selection of the correct intended operation, followed by execution stalling in the user interface or tool. This is not evidence of a domain-understanding gap; it is procedural tool-interaction failure or an environment defect. Treat it as a separate class from capability failure. Remediate with tool-interaction examples, interface affordances, or environment repair rather than more domain-task examples. Mislabel enough of these as capability failures and the team buys more data when it should fix the workbench.

**Banal-error clustering is itself diagnostic.** When 15% of failures trace to three or four specific environment quirks (a keyboard shortcut that does not exist, a tool that requires an undocumented preamble, a state the environment enters only under specific timing), the training signal is confounded. The model looks like it is failing at the domain when it is failing to learn a small number of mechanical workarounds. Report the quirk inventory alongside the failure distribution. A vendor who cannot enumerate the gotchas in their own environment has not evaluated their own dataset. The fix is usually environment engineering and not more data. The pattern also runs the other direction: the specific banal errors a model makes are informative commentary on where it sits on the procedural-fluency axis. An expert practitioner has internalized the workflow to the point where these errors are impossible. A capable reasoner who has never practiced in the tool will make them at high rates. Tracking the banal-error rate separately from the domain-reasoning error rate tells a lab whether the dataset is teaching procedural fluency in a specific tool-stack or teaching underlying domain reasoning. Those are different products.

**Environment artifacts masquerading as model errors.** Some failures look like model errors and are in fact environment errors the grader misattributes. The tool returned a stale value and the model acted correctly on the stale value. The environment dropped a mouse event and the next action arrived at the wrong state. These are orchestration-class failures in the narrow sense but they concentrate in environment infrastructure rather than in agent scaffolding. When failure triage shows a cluster of these, the grader’s assumption that the environment is faithful is the problem. Audit environment logs before auditing the model. Deterministic replay ([Stage 1](intake.md#stage-1-intake-review) artifact) is the tool for separating these: if the same inputs produce the same outputs, the environment is not the source of the failure; if they do not, the environment is the first thing to fix.

**Filter-by-low-pass-rate as a construction principle.** A dataset construction pattern that filters tasks down to “no current frontier model gets this right” produces a benchmark that looks impressive at release and saturates pathologically across one or two capability generations. The dataset is structurally locked outside the productive training band p in [0.25, 0.75] from day one and has no headroom story for the second model generation. Acceptable when the artifact is positioned as an evergreen eval and the buyer understands they are buying a benchmark, not training data; unacceptable when packaged as an OTS training product. [Stage 3](delivery.md#stage-3-packaging-for-lab-delivery) Q1 should reject any dataset whose construction principle is “filter for current-frontier failure” without a parallel training-band slice, regardless of the rubric quality. The fix is upstream of QC: ship both the hard filtered slice (as eval) and the unfiltered or band-targeted slice (as training data) under the same rubric.

**Construct-from-objective-ground-truth as the inverse positive pattern.** The clean alternative to filter-by-low-pass-rate is to construct questions from controllable properties of the underlying data (orthogonally validated metadata, experimental signals, structural lookups, instrumentation outputs) and let the difficulty fall out naturally. The pattern produces a benchmark with a naturally graded difficulty distribution. Some tasks turn out to be easy because the signal is loud, some turn out to be hard because the signal is faint, and a subset turns out to be beyond current capability because finding the signal from scratch is genuinely difficult under the time and tooling budget. Crucially, the hard subset is not pre-selected for failure; it emerges from the construction process. This avoids the saturation collapse that filter-for-failure produces, because the next model generation that improves on the hard subset is doing so against tasks that were always solvable in principle, not against tasks that were specifically engineered to defeat the prior generation. The pattern is the right default for any benchmark that intends to be evergreen across multiple capability generations, and pairs naturally with the validation-artifacts-at-construction-time intake requirement: the validation artifact establishes that the signal exists in the data, and the construction process establishes that the difficulty is a property of the data rather than a property of the filter.

**Domain-UI memorization masquerading as domain capability.** The inverse problem. A model that succeeds only when the exact UI of the training environment is present is not showing domain capability. It is showing memorized workflow. If the same task presented through a different interface produces a sharp performance drop, the model has learned the tool rather than the work. Tasks that succeed through UI-coupled shortcuts tell you less about the model’s understanding of the domain than the grader thinks. When the dataset is at all tool-coupled, evaluate domain generalization with held-out interface variants before certifying that training signal generalizes.

**Low-value task concentration.** The dataset is faithfully sourced and cleanly graded, but the tasks capture the commodity tier of the domain, the template-fill and reformatting a junior or a script handles, rather than the high-judgment work a senior practitioner is paid for. The model improves on the commodity tier and plateaus there. Headroom on the valuable tier is invisible because the valuable tier is barely represented. Check the value-tier distribution, not only the difficulty distribution. A clean dataset aimed at cheap work is still cheap data.

**Synthetic tells trigger eval-awareness.** The tasks are reasonable and the grader is sound, but the environment is dressed in filler. Placeholder names, throwaway email domains, the same fixture across every scenario. The model notices, infers it is being tested rather than deployed, and switches into test-taking behavior. It retrieves known answers, games the grader, or coasts. The trajectories look like capability or motivation failures and are in fact artifacts of the data announcing itself as fake. The fix is realistic fixtures, not a tighter rubric. This is the behavioral cousin of contrived tasks masquerading as real workflows. That pattern is about whether the task is real. This one is about whether the model can tell that it is not.

**Surface-level rubric from a non-practitioner.** The rubric is atomic, the criteria have clean kappa, and the grader is sound, but the criteria were written by someone who never did the work. They check that the output exists, has the right sections, and is formatted correctly, and they miss the judgment the work is actually about. A model trained against it produces outputs that pass every criterion and embarrass anyone in the domain. High inter-rater agreement does not save a rubric that measures the wrong things, since two non-practitioners can agree precisely on a surface check. The tell is a rubric whose criteria would all be satisfied by a confident, well-formatted, substantively wrong answer. Check who authored the rubric and whether the criteria encode practitioner judgment before trusting the kappa.
