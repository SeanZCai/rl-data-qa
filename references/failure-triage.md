### [Both] Model failure examination

The grader tells you a rollout failed. It does not tell you why. For a small model post-trained on a vendor dataset, a failure has several plausible root causes, and the remediation for each is different. Treating every failure as evidence of a capability gap is how teams end up spending training budget on a dataset that actually has a prompt design problem, a rubric problem, or a tooling problem that looks like capability failure from the outside. Before approving or rejecting a dataset on the basis of post-training performance, run an LLM-as-judge pass dedicated to failure triage. This is a separate pass from the grader. It does not re-score the task. It classifies the failure. Run this pass after the manual trajectory review, against the taxonomy that pass calibrated, and treat the solvability test as the gate that precedes any label. A failure a qualified person could not have solved with the model's own context is an environment defect and is set aside before the judge assigns a cause.

The judge reads the failed rollout alongside the task specification, the gold output, and the rubric, and assigns one of the following labels:

- **Capability failure.** The task is solvable under the provided context and tools, and the agent's observable actions and intermediate artifacts pursue a valid method under the required constraints, but execution fails at a specific step the model cannot complete. Cite the assistant-visible message, action, tool result, state transition, or artifact that establishes both valid progress and the breakdown; do not infer private reasoning or require the intended path.
- **Prompt defect.** The task framing is underspecified, ambiguous, or actively misleading. A qualified human given the same prompt would also produce a wrong answer, or would ask a clarifying question. The failure is not diagnostic of the model.
- **Scaffolding defect.** The model had no way to access information it needed. The environment gave the model a broken tool, withheld a tool it should have had, or structured the interaction so the model couldn’t see context the gold solution depends on.
- **Rubric defect.** The grader marked the rollout wrong, but the rollout is defensibly correct. The rubric is too narrow, rewards format over substance, or fails to credit an alternate valid solution path. This overlaps with verifier stress testing but surfaces at per-example granularity that aggregate false positive and false negative rates hide.
- **Training data defect.** The model is failing because the dataset taught it the wrong pattern. The rollout shows a learned shortcut that generalizes badly, or a behavior directly traceable to a pathology in specific training examples: wrong demonstrations, inconsistent labels, or reward hacking reinforced during post-training.
- **Orchestration defect.** Multi-step tasks where the failure sits at a handoff or state boundary rather than in an observable decision or action. The agent completed step one correctly and step two correctly, then the orchestration layer dropped state or retried with stale context. This class gets misread as a capability failure and is overcounted in long-horizon traces.
- **Triangulation failure.** The task description, the verifier, and the prompt given to the model are not coherent with one another. The prompt asks for one thing, the task description expects another, and the rubric scores a third. The rollout fails because these three artifacts disagree. The model is not the source of the failure. This class is detected by reading the three artifacts side-by-side. Trace inspection alone will miss it.

#### Prompt defect decomposition

Label 6, prompt defect, collapses several distinct problems together. When the aggregate report shows prompt defects above 20%, the remediation advice 'return to vendor for revision' is not actionable unless you know which kind of prompt defect dominates. Split the prompt defect label into the following sub-classes and have the judge pick one:

- **Prompt-underspecified.** The prompt omits information the task requires. A qualified human would either guess or ask. A debugging task that does not specify which codebase state the failure reproduces against is the canonical example.
- **Prompt-contradictory.** The prompt contains two directives that cannot both be satisfied. 'Return results sorted by date' and 'return results in the order matching the input list' is the archetypal case. Models that detect the contradiction pick one and the grader fails them for not following the other.
- **Prompt-buried-context.** The information the model needs is in the prompt, but several paragraphs away from the directive that requires it, interleaved with irrelevant context. A careful human reader would catch it. A model running at pass@1 latency will not.
- **Prompt-unstated-domain.** The task assumes domain knowledge the prompt does not supply and the model cannot reliably produce from priors. 'Interpret this ICD-10 code' without the code lookup table is one case. 'Use the company's internal style guide' without the guide attached is another.
- **Prompt-format-gap.** The prompt specifies what to do but not how to return the answer, and the grader is format-sensitive. The model produces a defensible answer in the wrong shape and loses credit for a reason unrelated to substantive task performance.
- **Prompt-rubric-drift.** The rubric expects a specific step or artifact that the prompt does not cue the model to produce. This is a triangulation failure when it is a three-way artifact disagreement. It is a prompt defect when it is only the prompt that diverges from what the rubric wants.

When the judge returns prompt-underspecified through prompt-rubric-drift, the vendor gets a task-level list of which tasks need which specific rewrite. The aggregate number '22% prompt defect' becomes six smaller numbers that each map to a different edit action.

#### Scaffolding and process defect decomposition

Label 7, scaffolding defect, is similarly coarse. Environments fail in characteristically different ways and the remediation differs per mode. Split the scaffolding defect label:

- **Scaffolding-tool-absent.** The gold solution calls a tool the model did not have access to. The model attempted the task with the wrong tools or no tools.
- **Scaffolding-tool-broken.** The model called a tool that existed in the environment but returned an error unrelated to the model's input. Sandbox timeouts. Dependency resolution failures. Network partitions.
- **Scaffolding-tool-silent-failure.** The tool returned an output, the model treated it as signal, but the output was empty, stale, or a default error message that did not surface as an error. This is the worst class in the taxonomy because the assistant-visible output can look like a capability failure; the defect appears only when the actual tool result and environment state are compared with the expected response.
- **Scaffolding-action-mismatch.** The model's affordances diverge from what the task's gold solution assumes. Either the model has actions the gold does not use, or the gold uses actions the model cannot invoke. Both show up as capability failures to a casual reader.
- **Scaffolding-state-passing.** Multi-turn tasks where the orchestration layer dropped context between turns, retried with stale state, or returned the wrong turn's output. This overlaps with orchestration defect but sits at the environment interface rather than in the agent's own loop. Catch it by diffing the model's expected input at turn N against what the orchestration layer actually handed it.
- **Scaffolding-context-exhausted.** The task loaded enough context that the model hit a truncation boundary during the run and lost access to task-relevant material mid-task. The failure looks like forgetting, but the cause is mechanical.
- **Scaffolding-feedback-absent.** The environment was supposed to return a signal, an error message or a tool response or a test result, that would let the model course-correct. The signal was absent or returned as a generic success code. The model proceeded on false confidence.

Check whether the scaffolding sub-class reproduces across the dataset or is confined to specific tasks. A scaffolding-tool-silent-failure rate of 40% across failing rollouts points to a sandbox bug. A pattern across the five tasks that use a specific tool points to a broken integration for that tool.

The judge does not produce useful triage if you ask it to freely grade. It needs structured system context with the decision criteria spelled out. The checklist below provides system prompt material for the failure triage pass. It is the minimum. Vendors operating in specialized domains will add dimensions.

#### Judge model system context checklist

- **Is the task specification self-contained?** A qualified domain expert reading only the task prompt should be able to produce a correct solution without guessing the evaluator’s intent. If not, the failure leans prompt defect.
- **Does the rubric credit every valid way of satisfying the declared objective?** If the outcome and state are correct and every explicitly scored observable constraint is met, an unfamiliar method is not a failure. The failure leans rubric defect when the judge penalizes deviation from a reference solution or an unstated preferred path. Compare observable outputs, actions, tool results, state transitions, and artifacts against the rubric; do not request private reasoning or require a rubric-sanctioned method unless that method is itself the stated capability or production constraint.
- **Were all tools and context the gold solution uses available to the model at the time of the failed step?** If the gold solution relies on a tool call that was missing, broken, or returning stale output, the failure is scaffolding.
- **Do observable events distinguish a task-selection or planning error from an execution, tool, or state-passing error?** Use assistant-visible commitments when they are emitted as task output, together with chosen actions, tool responses, state transitions, intermediate artifacts, and the final output. Do not request private chain-of-thought. A valid alternative strategy receives full credit; classify a strategy error only when observable behavior violates the objective, an explicit constraint, or the rubric.
- **Is this failure consistent with the training data’s pathologies?** If the observable rollout behavior matches a specific demonstration type in the training set (truncated work products, missing intermediate artifacts, format-over-substance outputs, or memorized surface patterns), the failure is a data defect.
- **Would a domain expert, unaided by reference material, fail this task under the same scaffolding?** If yes, and the task claims to represent a capability the model should have, the prompt or environment is not faithful to the underlying work.
- **Is the failure in an observable decision or action selection, or in state passing between turns or actions?** Orchestration-layer failures get confused with capability failures in long agent traces. Examine tool-call boundaries, state transitions, handoffs, retry context, and intermediate artifacts explicitly.
- **Is the failure mode reproducible across independent rollouts of the same task?** A failure that is stochastic across rollouts but consistent in shape is usually a model or data issue. A failure that is deterministic across rollouts almost always involves the task specification, scaffolding, or grader.
- **Does the rollout exhibit reward-hacking behavior consistent with patterns surfaced during reward hacking probes?** If so, the failure is a consequence of the data’s reward signal, not the model’s capability.
- **Does the rollout show evidence the model detected the environment was synthetic?** Retrieval of a known public answer, an abrupt collapse in effort, or behavior aimed at the grader rather than the task are tells that the failure is an eval-awareness artifact of the data rather than a capability gap. Weight the triage toward data defect when these appear.
- **Is there specification gaming, where the model optimizes for the literal text of the rubric over task intent?** This is a data defect, not a model defect.
- **Does the failure reproduce across independent models?** If frontier models at the top of the capability distribution also fail the task, the label leans prompt defect, scaffolding defect, or rubric defect. If only the post-trained model under evaluation fails, the label leans capability failure or training data defect. A failure that only shows up in the small model is diagnostic. A failure that shows up everywhere is about the task, not the model. Cross-model variation is what the vendor’s cross-model results table exists to enable.
- **Has the judge been given the agent’s full specification?** The judge needs the system prompt, scaffolding architecture, tool schemas, and action space boundaries as part of its context. A judge operating without this cannot distinguish capability failure from scaffolding failure because it does not know what the model could and could not do. Include the agent spec in the judge’s system context alongside the task, rubric, and gold trace.
- **What is the task’s provenance?** Real incidents, production logs, and expert-reconstructed tasks should carry a higher prior on the “capability failure” label when the rollout fails. Contrived scenarios should be priced with a lower prior. A failure on a task that no practitioner has actually faced is more often a sign that the task is not realistic than a sign that the model is weak. Weight the triage accordingly.
- **Do the task description, the rubric, and the prompt agree?** Read the three artifacts together. If they diverge, the failure is a triangulation failure rather than a model defect. This check costs almost nothing and surfaces a class of failure the other checklist items will miss.
- **Has the pass@k and mean score profile of the failing task been checked against the vendor’s calibration numbers and against cross-model rollouts?** A task that the vendor reports as hard but frontier models all pass at pass@5 is mislabeled. A task that the vendor reports as in the productive training range but nothing passes at pass@10 is likely not reached at this stage of training, and failure there carries no signal.
- **Is the task’s verification asymmetric?** Is it easier to check the answer than to produce it? On tasks low on the asymmetry axis, judge verification is unreliable and the failure class itself becomes suspect. Flag these rollouts as low-confidence triage rather than force a label.

#### Extending the judge's system context for agentic datasets

Items above are the minimum. When the vendor's dataset uses agentic scaffolding, multi-turn interaction, or tool use, extend the judge's system prompt with the following:

- **What tool was available at each step of the failed rollout, and what did each tool return?** The judge needs the observable transcript and full tool-call log, not any private reasoning trace. A rollout that looks like a capability failure from the assistant-visible text alone is often a silent tool failure once the tool output and environment state are aligned with the transcript.
- **Did the model's context window stay under its effective attention budget during the rollout, not just under the hard token limit?** Models degrade before they truncate. Include the running context length per turn and flag rollouts where this crossed 70% of the limit before failure.
- **Does the failure sit at a turn boundary?** For multi-turn rollouts, include the exact turn where the first evidence of failure appears, and whether the preceding turn's output was passed to the next turn faithfully. This catches state-passing failures without requiring the judge to reconstruct orchestration semantics.
- **Is the prompt defect sub-class in the judge's label vocabulary?** Prompt-underspecified, prompt-contradictory, prompt-buried-context, prompt-unstated-domain, prompt-format-gap, and prompt-rubric-drift should each be available as a discrete label. If the judge can only return 'prompt defect' unsubscripted, the aggregate report cannot tell the vendor which edits to make.
- **Is the scaffolding defect sub-class in the judge's label vocabulary?** Same for tool-absent, tool-broken, tool-silent-failure, action-mismatch, state-passing, context-exhausted, and feedback-absent.
- **Include at least three calibration examples per sub-class** in the judge's few-shot context. Prompt-contradictory versus prompt-underspecified is a subtle distinction and the judge will conflate them without calibration. Six sub-classes times three examples is eighteen calibration shots for prompt defects alone, plus another twenty-one for scaffolding. The judge prompt grows. So does the signal-to-noise ratio of the triage.
- **Give the judge a low-confidence escape hatch.** A triage label of 'ambiguous, needs human review' with a free-text explanation field is strictly better than forcing a label. A 5% escape rate is normal and worth auditing. A 30% rate means the judge is undercalibrated, the rubric is under-specified, or both.
- **Require the judge to cite evidence at two levels.** First, quote the specific observable turn, tool call, state transition, rubric criterion, or prompt segment that justified the label.

Second, quote the model's own failed output verbatim, not paraphrased, as a separate field in the judge's response. 'Capability failure because the assistant's turn 4 output states that the inverse of a square matrix is computed by negating each element, and the next observable action applies that invalid rule' beats a bare label every time. The second-level citation preserves the texture of the failure. A lab reading the aggregate report can see how the model was wrong, not only that it was. This adds length to the judge's output and makes the report substantially more diagnostic. It also lets you spot-check the judge itself at minimal cost because the verbatim excerpt is independently re-readable; private chain-of-thought is not evidence the package should request or expose.

- **Run the judge twice on a 10% sample**, with a different seed and reordered input context, and report the agreement rate. A judge that returns different labels on the same rollout with prompt reordering is not a measurement instrument. If agreement falls below 85%, the system context is under-specified rather than the judge being weak.
- **Preserve chain of custody from grader to judge.** The judge must read the grader's full criterion-level output, not just the binary pass/fail. A rollout that scored partial credit the grader collapsed to 'fail' at the margin is a different failure class than one that missed every criterion.
- **Version the judge prompt alongside the dataset version.** A QC report generated with judge prompt v1.2 and aggregated against a dataset tested under judge prompt v1.4 is not comparable. Pin the judge prompt hash in the QC output and treat prompt changes as version bumps, not tunings.

The judge pass produces a label per failed rollout. Aggregate the labels across the dataset. The distribution is the diagnostic output.

- **Capability failures dominating**, above 60% of failed rollouts labeled as such, with observable transcript, tool-call, state, and final-output evidence supporting the label: the model is below the dataset’s difficulty frontier. This is the expected pattern for a dataset in the productive training range.
- **Prompt and scaffolding defects together exceeding 20% of failures:** the dataset has an instruction design problem. Return to vendor for revision. These are not training signal. They are noise.
- **Rubric defects exceeding 10%:** run a second verifier stress test against a broader test suite. If the signal persists, the grader is under-specified relative to task complexity. Rework the rubric before accepting the dataset.
- **Training data defects at any meaningful rate, above 5%**, after a clean post-training run: the dataset contains demonstrations that actively degrade the model. Trace them, isolate them, and flag the vendor’s pipeline as suspect until root cause is identified.
- **Orchestration defects exceeding 15% on long-horizon tasks:** the environment is unstable. The dataset is not evaluable until the environment is fixed, regardless of what the grader scores.
- **Triangulation failures at any meaningful rate, above 3% of failed rollouts** on the sample audited: the dataset’s core artifacts are out of sync with one another. Return to vendor for rework before any other signal is trusted. Other class labels drawn from a mis-triangulated sample cannot be priced.

Two operational notes. Use a strong frontier judge for this pass. The post-trained model you are evaluating is not qualified to diagnose itself, and a weaker judge defaults to “capability failure” because the alternative categories require reading more context than the weaker judge will successfully carry. Second, keep the judge’s system context under version control. Failure triage is one of the few places in the QC process where the scaffolding itself is part of the measurement, and small changes to the judge’s framing shift the label distribution meaningfully. Treat the judge prompt as a released artifact that accompanies the QC report, not as a free variable.

**[Per-model decomposition](requirements.md#m14-both-per-model-failure-class-breakdown-report) is required for delivery.** The aggregate failure-class distribution is informative but not sufficient. Different model families exhibit characteristically different failure shapes. One family clusters on prompt-underspecified failures, another on scaffolding-tool-silent-failure, a third on capability. The per-family decomposition is what labs use to triage capability gaps from harness artifacts. Ship the full failure taxonomy with per-model breakdown, sample-size caveat, and two to three worked example failures per bucket per model. The deliverable form is a per-model failure-class report, customized at the model-family level, available as an artifact alongside the leaderboard and on request per-lab. With fewer than approximately 100 reviewed rollouts per model, per-tag rates below 5% are illustrative rather than significant.

**[Cross-task aggregated failure-pattern analysis](requirements.md#m15-both-cross-task-aggregated-failure-pattern-report) is required alongside the per-model decomposition.** [Per-model decomposition](requirements.md#m14-both-per-model-failure-class-breakdown-report) tells the buyer how a model fails across the dataset. Cross-task aggregated analysis tells the buyer which classes of failure recur across tasks regardless of model. The dataset-level pathology view. If 40% of failed rollouts across the dataset cluster on scaffolding-tool-silent-failure on the email API, the dataset has a structural problem the per-model view cannot surface. Ship a cross-task failure-class histogram alongside the per-model breakdown, with sub-class breakdown and named clusters above the 5% threshold.

#### Judge prompt template

The following skeleton is the minimum the failure-triage judge should receive as system context. Extend per domain, per scaffolding class, and per rubric architecture.

You are a failure triage judge for reinforcement learning post-training datasets. You read a single failed rollout and classify the cause of failure. You do not re-score the task. You do not produce a corrected answer.

You will receive (1) the task specification, (2) the rubric including partial-credit breakdown, (3) the gold-standard output if available, (4) the model's full observable rollout including assistant-visible messages, every tool call with its input and output, relevant state transitions, and the final output, (5) the grader's criterion-level scoring, (6) the agent's system prompt and action-space specification, (7) reward-hacking probe results for this task if any were run, (8) cross-model results if this task was run against multiple models. Do not request or infer private chain-of-thought.

You will return exactly one label drawn from this enum. capability, prompt-underspecified, prompt-contradictory, prompt-buried-context, prompt-unstated-domain, prompt-format-gap, prompt-rubric-drift, scaffolding-tool-absent, scaffolding-tool-broken, scaffolding-tool-silent-failure, scaffolding-action-mismatch, scaffolding-state-passing, scaffolding-context-exhausted, scaffolding-feedback-absent, rubric-defect, training-data-defect, orchestration-defect, triangulation-failure, ambiguous-needs-human-review.

For each label, you will cite the specific turn number, tool call, rubric criterion, or prompt segment that justifies the label. You will quote the relevant passage verbatim. You will not speculate beyond what the evidence supports. If the evidence is insufficient for any of the above labels, you will return ambiguous-needs-human-review with a free-text explanation of what the rollout is missing.

This is a template, not a finished prompt. The calibration examples, domain-specific extensions, and few-shot pairs are left to the operator. The template fixes the output schema, the evidence requirement, and the label enum. Everything else is tuning.

#### Debugging loop

Triage is not the end of the pipeline. It is the beginning of a second loop. When the aggregate report returns a distribution like 'capability 45%, prompt-underspecified 18%, prompt-buried-context 9%, scaffolding-tool-silent-failure 11%, other 17%', the vendor has a concrete work list. Rewrite the tasks the judge flagged as prompt-underspecified, using the judge's cited segments as targets. Instrument the sandbox tool that scaffolding-tool-silent-failure clustered around. Re-run the post-training pass against the revised dataset. Re-run the judge. Compare distributions.

The first pass surfaces problems. The second pass tells you whether the remediation worked. Datasets that do not converge across two triage passes are the ones where the vendor should stop shipping and start asking different questions about the pipeline itself.
